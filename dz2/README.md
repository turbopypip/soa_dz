# ДЗ 2 — Marketplace: OpenAPI + CRUD

Реализация всех десяти пунктов задания: OpenAPI, генерация DTO и HTTP-обработчиков, PostgreSQL + Flyway, CRUD, контрактные ошибки и валидация, заказы/промокоды, JSON-логи, JWT и роли.

## Запуск

Нужен Docker с Compose. Из каталога `dz2`:

```bash
docker compose up --build -d --wait
docker compose logs migrate api
```

API: http://localhost:8080, Swagger UI: http://localhost:8080/docs. Swagger использует исходную OpenAPI-спецификацию. База доступна только внутри сети Compose. Если порт занят, запустить с `API_PORT=8081 docker compose up --build -d --wait`.

Настройки приведены в `.env.example`; при необходимости скопировать в `.env`. Значения по умолчанию предназначены для локальной защиты. Администратор создаётся при первом запуске: `admin` / `admin-password`. Регистрация позволяет выбрать `USER` или `SELLER`; получить роль `ADMIN` через публичный API нельзя. Изменение переменных администратора не сбрасывает пароль уже существующего пользователя.

```bash
# Интеграционные тесты с настоящим PostgreSQL
docker compose exec -T api pytest -q

# Полный HTTP-сценарий и SELECT содержимого всех бизнес-таблиц
docker compose exec -T api python scripts/demo.py

# Посмотреть БД вручную
docker compose exec db psql -U marketplace -d marketplace
```

В psql:

```sql
SELECT installed_rank, version, description, success FROM flyway_schema_history;
SELECT id, name, price, stock, status, seller_id FROM products;
SELECT id, user_id, status, total_amount, discount_amount, promo_code_id FROM orders;
SELECT order_id, product_id, quantity, price_at_order FROM order_items;
SELECT code, current_uses, max_uses FROM promo_codes;
SELECT user_id, operation_type, created_at FROM user_operations ORDER BY created_at;
```

`demo.py` рассчитан на стандартный лимит в одну минуту. Он создаёт уникальные аккаунты, поэтому повторный запуск не требует очистки БД. Тесты также создают собственные записи с уникальными именами, ничего не очищают и отключают лимит только в своём процессе, кроме теста ограничения частоты. Для ручного просмотра выбирайте нужные записи по ID из вывода демонстрации.

Остановка с сохранением БД: `docker compose down`. Не добавляйте `-v`, если данные нужно сохранить.

## Контракт и генерация

- `src/main/resources/openapi/openapi.json` — исходный OpenAPI 3.0.3: запросы, ответы, ограничения, каталог ошибок, security и роли.
- `scripts/generate.py` — одна команда для генерации: `python scripts/generate.py` (или `make generate`).
- `datamodel-code-generator` генерирует Pydantic DTO. Тот же скрипт читает `operationId`, параметры, схемы тел и ответов и генерирует FastAPI-обработчики, которые вызывают бизнес-сервис. Генератор обработчиков небольшой и хранится в репозитории.
- `app/generated/` исключён из Git и Docker build context. Dockerfile всегда генерирует его заново при сборке. Не редактировать сгенерированные файлы вручную.
- Ручных DTO нет. `app/model_base.py` задаёт только сериализацию Decimal как JSON number, как требует контракт.
- `app/validation.py` проверяет JSON прямо по контракту до вызова обработчика: типы, диапазоны, длины, UUID, date-time, nullable, дополнительные поля. Затем запрос проверяется сгенерированной Pydantic-моделью. Для массива позиций контракт содержит расширение `x-unique-by: product_id` — дубликаты запрещены.

Локальная генерация без контейнера:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python scripts/generate.py
```

## Устройство приложения

| Файл | Ответственность |
|---|---|
| `app/generated/routes.py` | Сгенерированные маршруты и привязка DTO |
| `app/service.py` | CRUD, заказы, промокоды, проверки бизнес-инвариантов |
| `app/db.py` | Соединение PostgreSQL, транзакции и блокировка записей |
| `app/security.py` | Argon2, JWT, роли, bootstrap администратора |
| `app/main.py` | Middleware, формат ошибок и JSON-логирование |
| `app/validation.py` | Валидация исходного контракта |
| `migrations/V1__marketplace.sql` | Миграция Flyway, таблицы, ограничения, индексы, триггеры |
| `tests/test_marketplace.py` | Интеграционные и конкурентные сценарии |

Все бизнес-изменения выполняются в транзакции psycopg. Исключение автоматически откатывает всю операцию, включая остатки, промокод и журнал операций. Для учебной нагрузки используется одна `pg_advisory_xact_lock` на записи: она действует между процессами/репликами приложения и освобождается при commit/rollback. Это простой способ исключить overselling, двойное использование последнего промокода и гонки активных заказов. Компромисс — операции записи сериализованы. Для большой нагрузки можно перейти на блокировки строк в устойчивом порядке; здесь сложность этого решения не нужна. Дополнительно БД содержит частичный уникальный индекс одного активного заказа на пользователя.

Чтение страницы товаров и заказа использует `REPEATABLE READ`, чтобы несколько SELECT видели согласованный снимок. Даты создаются через defaults, `updated_at` обновляется триггером. DELETE товара меняет статус на `ARCHIVED`; заказ и история позиций сохраняются.

Деньги считаются в `Decimal`, в БД — `NUMERIC(12,2)`. В запросах цена передаётся JSON-числом с точностью до копеек. Округление скидки — `ROUND_HALF_UP`. Сумма заказа ограничена вместимостью `NUMERIC(12,2)`; переполнение возвращает `VALIDATION_ERROR` с rollback.

## Принятые решения по неоднозначностям условия

1. Для процента до 70 включительно применяется указанная скидка. Для процента выше 70 скидка равна нулю: это буквальное прочтение «в ином случае цена 100%». Фиксированная скидка ограничивается суммой заказа.
2. При изменении количества уже заказанного товара сохраняется его `price_at_order`. Новые товары получают текущую цену. Изменение каталога не меняет ранее зафиксированную цену.
3. При обновлении заказа его собственное использование промокода не считается новым. Промокод с `max_uses=1` можно пересчитать в уже использующем его заказе. Истёкший/неактивный промокод даёт ошибку с полным откатом; недостаточная новая сумма снимает скидку и освобождает использование, как требует условие.
4. Отмена разрешена из `CREATED` и `PAYMENT_PENDING`, согласно тексту задания. Повторная отмена запрещена, поэтому остатки и счётчик не возвращаются дважды.
5. Добавлен `POST /orders/{id}/status` для ADMIN, чтобы продемонстрировать цепочку `CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED`. Отмена выполняется отдельным `/cancel`.
6. Создание товара назначает владельцем текущего продавца/администратора. ADMIN может изменять любые товары и заказы; SELLER — только свои товары. `USER` и `SELLER` доступны через самостоятельную регистрацию.
7. Остаток в PUT товара — доступный, уже за вычетом резервов. При изменении только цены передавайте актуальный остаток из GET.

## Авторизация и ошибки

Access JWT живёт 20 минут, refresh JWT — 14 дней. Проверяются подпись HS256, issuer, audience, exp, тип токена и пользователь/роль в БД. Refresh не подходит для обращения к CRUD. Пароли хранятся в виде Argon2-хеша. Refresh-токены в учебной версии не отзываются и не являются одноразовыми.

Все бизнес-эндпоинты требуют `Authorization: Bearer <access_token>`. `/auth/*` и документация доступны без авторизации. JWT содержит `sub`, `role`, `type`, `iat`, `exp`, `jti`, `iss`, `aud`.

```json
{
  "error_code": "INSUFFICIENT_STOCK",
  "message": "Insufficient stock",
  "details": {
    "products": [{"product_id": "UUID", "requested": 5, "available": 2}]
  }
}
```

При валидации `details.violations` содержит поля и причины. У каждого ответа есть `X-Request-Id`; middleware генерирует UUID и пишет одну JSON-запись с методом, путём, статусом, временем, длительностью и user_id. У мутирующих запросов записывается тело с маскированием паролей, токенов и секретов. Некорректный JSON целиком исключается из логов.
